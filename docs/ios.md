# iOS Integration

This document is the issue-#470 iOS integration recipe for shipping `wirelog`
through `wirelog.xcframework` and consuming it from Swift.

## Build artifact for iOS

`wirelog.xcframework` is generated by
`scripts/package-ios-xcframework.sh` (out-of-Meson helper). It is not wired
into default Meson targets.

Prerequisites for a reproducible local build:

- Xcode 16.4 (`DEVELOPER_DIR=/Applications/Xcode_16.4.app/Contents/Developer`)
  because CI is pinned to that exact toolchain.
- iOS minimum deployment target `13.0`.
- Xcode command-line tools from `xcrun`.

Run:

```sh
scripts/package-ios-xcframework.sh \
  --output dist/ios \
  --build-root builddir-ios-xcframework
```

The script builds three slices from:

- `cross/ios-arm64.ini` (`ios-arm64`)
- `cross/ios-simulator-arm64.ini` (`ios-simulator-arm64`)
- `cross/ios-simulator-x86_64.ini` (`ios-simulator-x86_64`)

The two simulator archives are **fat-packed** with `lipo` before XCFramework
assembly so the `Simulator` slice in `wirelog.xcframework` contains both
`arm64` and `x86_64`.

Each packaged library path is a static archive (`libwirelog.a`) and each slice
receives public headers plus `wirelog/module.modulemap`.

## Consume via SwiftPM binary target

Point `wirelog.xcframework` to a local path `binaryTarget` in `Package.swift`:

```swift
let package = Package(
    name: "MyLib",
    platforms: [.iOS(.v13)],
    products: [
        .library(name: "MyLib", targets: ["MyLib"]),
    ],
    targets: [
        .binaryTarget(
            name: "wirelog",
            path: "../dist/ios/wirelog.xcframework"
        ),
        .target(
            name: "MyLib",
            dependencies: ["wirelog"]
        ),
    ]
)
```

Because the headers are packaged with `wirelog/module.modulemap`, Swift can import
the C API directly:

```swift
import wirelog
```

## Register an adapter from Swift

Use the current public adapter API names (`wirelog_io_register_adapter`, etc.)
and the trailing `user_data` argument for state.

```swift
import Foundation
import wirelog

private final class AdapterContext {
    let sourceURL: URL
    init(sourceURL: URL) { self.sourceURL = sourceURL }
}

private let readCallback: @convention(c) (
    OpaquePointer?,
    UnsafeMutablePointer<UnsafeMutablePointer<Int64>?>?,
    UnsafeMutablePointer<UInt32>?,
    UnsafeMutableRawPointer?
) -> Int32 = { ctx, outData, outRows, userData in
    let _ = ctx
    guard let rows = outRows, let dataOut = outData else {
        return -1
    }

    let state = userData
        .map { Unmanaged<AdapterContext>.fromOpaque($0).takeUnretainedValue() }
    _ = state  // Access user data if needed.

    rows.pointee = 0
    dataOut.pointee = nil
    return 0
}

private var adapterStorage: wirelog_io_adapter_t = {
    let scheme = strdup("memory")
    let description = strdup("bundle-backed adapter")
    precondition(scheme != nil && description != nil)

    return wirelog_io_adapter_t(
        abi_version: WIRELOG_IO_ABI_VERSION,
        scheme: scheme!,
        description: description!,
        read: readCallback,
        validate: nil,
        user_data: nil
    )
}()

private func registerBuiltinAdapter(context: AdapterContext) -> Int32 {
    let userData = Unmanaged.passUnretained(context).toOpaque()
    adapterStorage.user_data = userData
    return wirelog_io_register_adapter(&adapterStorage)
}
```

Store `context` to keep it alive for callback lifetime.
The Swift side owns that lifetime, and keeps a single `AdapterContext`
instance alive for as long as the adapter is registered.

```swift
let context = AdapterContext(sourceURL: someURL)
let rc = registerBuiltinAdapter(context: context)
precondition(rc == 0, "register failed: \(String(cString: wirelog_io_last_error()))")
```

To unregister:

```swift
_ = wirelog_io_unregister_adapter("memory")
```

Avoid `Unmanaged.passRetained` here; this API expects a borrowed
`UnsafeMutableRawPointer` (`user_data`), so `passUnretained` matches the callback
lifetime contract.

## Bundle/resource path handling on iOS

When loading packaged `.dl` or CSV assets, resolve paths via bundle APIs rather
than hard-coded `/tmp` or absolute paths:

```swift
func resourcePath(_ name: String, ext: String) -> String? {
    guard let url = Bundle.module.url(
        forResource: name,
        withExtension: ext
    ) else {
        return nil
    }
    return url.path
}

guard let path = resourcePath("program", ext: "dl") else {
    throw NSError(domain: "wirelog-ios", code: 1, userInfo: nil)
}
```

## Threading guidance

Parsing, planning, and evaluation should not run on the main actor.

- Prefer `Task.detached` for async startup/evaluation:
  - `Task.detached(priority: .utility)` for Swift concurrency paths.
- If your app is not structured-concurrency-first, use
  `DispatchQueue.global(qos: .userInitiated).async { ... }`.

Return parsed results back to the UI on the main actor only.
Also keep each `wirelog_session_t` / easy-session handle confined to one
execution context, or externally serialize access. Do not invoke wirelog
APIs concurrently on one shared handle from multiple threads or tasks.

## App Store / review constraints

- `wirelog.xcframework` produced by the script is a static bundle; no runtime
  `dlopen` of `wirelog_io_plugin_entry` is required for normal consumers.
- The CLI plugin path is optional and out-of-band; for iOS app shipping, prefer
  static linkage and direct API registration through public entry points.
- Keep this as plain C API usage in a static linkage model to minimize dynamic
  loading concerns in Apple review.

## Build flag notes

- Xcode versions newer than 16.4 may emit `bitcode`-related warnings; avoid
  forcing bitcode settings that are deprecated for current iOS toolchains.
  Ensure the app target does not enable legacy bitcode generation.
- If you observe adapter or registration symbols being removed by aggressive linker
  pruning, verify `-dead_strip`/`-ObjC` policy and add an explicit
  `-force_load` for `libwirelog.a` when testing.

## Privacy manifest

`wirelog` itself does not invoke privacy-sensitive Apple APIs and does not
require any Required Reason API entries in the app's `PrivacyInfo.xcprivacy`.
The app still owns its own privacy manifest and must include Required Reason
entries for APIs it uses directly (camera, location, contacts, etc.).
